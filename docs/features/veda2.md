# Veda2：stage1（冻结 backbone、只训 adaptor）下的改法

## 目标

在**不改 kernel、不降速度**的前提下，把 stage1 的效果做到最好。stage1 的目标函数就是
ε，即稀疏输出相对稠密教师的误差（定义见 [sol_ablation](sol_ablation.md) §1），因为
backbone 冻结、模型不会自己适应稀疏。

结论先写：**Veda2 = 块质量目标 + 打分器补上「块行数」与「二阶矩」两个特征 + 静态的每头
预算**。三项都是零推理成本、零 kernel 改动。实测在 16:9@37 上每头 ε 中位数降 8~12%，
加上每头预算再降约 6%。**零阶补偿不进 Veda2**，理由见 §5。

## 1. 诊断：瓶颈是打分器，而且是结构性的

[sol_ablation](sol_ablation.md) 已经量出：打分器不准要吃掉 18~43% 的误差，是换蒸馏目标
（7~10%）的 2.4~4.3 倍。本文档回答「那打分器该怎么改」。

关键观察是**打分器的初始化本身就是在估计块的对数质量**。`predictor.py` 把 P 初始化成
N(0, 1e-4)，于是未训练的打分器精确等于均值池化的 QK，而那正是块对数质量的零阶项：

```
log E_ij = log B_j + Qbar_i . Kbar_j / sqrt(D) + Qbar2_i^T Cov_j Qbar2_i / (2D) + ...
            ^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
            缺失      现有打分器只有这一项          缺失
```

两个缺失项都**不是容量问题，是特征问题**：

- `log B_j` 是块里真实行数的对数。打分器看不到行数，所以它把一个只有 32 行真实 key 的
  补齐块和一个 128 行的满块排在同等位置。但块的注意力**质量**与行数成正比。
  16:9@37 的 (37,24,42) 网格用 4x4x8 排列要补到 (40,24,48)，最后一个 t 块只有 1/4 真实
  帧、最后一个 w 块只有 2/8 真实列，所以补齐块占比不小，这个偏差是系统性的。
- 二阶项需要 query 侧的 `E[q^2]` 和 key 侧的 `Var(k)`。双线性形式作用在
  `[mean|max|min]` 上，而方差是均值的二次函数，线性投影**构造不出来**，无论怎么训。

一个自洽的细节：现在的蒸馏目标是块内**最大**概率 `Mx`，而 max 几乎不随块行数变化，所以
「看不到行数」在 max 目标下是**正确的**。也就是说目标和特征是配套的——要改一个就得改另一个。

## 2. 实测：两个缺失项各值多少

16:9@37（38010 token、366 tile）、8 步 Turbo 教师 + step600 LoRA、`moviegen_holdout20`
2 条 prompt × 步 {0,2,5,7} × 50 层 × 56 头 × 6 个密度 = 134400 行，每头抽 6 个 query tile。

「补回的差距比例」= `(ε_proxy − ε_变体) / (ε_proxy − ε_oracle)`，0 表示和未训练的池化分数
一样，1 表示和知道答案一样好：

| ρ | proxy（现状） | +log B | +对角二阶 | +完整二阶 | A（质量 oracle） | Mx（最大 oracle） |
|---|---|---|---|---|---|---|
| 5% | 0.0% | **36.3%** | **46.0%** | 38.8% | 92.9% | 63.6% |
| 10% | 0.0% | 27.2% | **32.9%** | 33.6% | 92.1% | 82.2% |
| 20% | 0.0% | 21.9% | **26.9%** | 33.6% | 94.1% | 85.3% |

三件事：

1. **光加 `log B` 就补回 22~36%**，而它是每块一个常数，从 layout 直接读，成本为零。
2. **对角二阶项再加到 27~46%**，而且**稀疏度越高收益越大**，正好是稀疏加速关心的区间。
3. **完整二阶项并不更好**：ρ=5% 时对角（46.0%）反而**超过**完整（38.8%）。截断的累积量
   展开本来就不保证加更多项更准，而完整项需要 rank D² 的双线性，推理期根本付不起。
   **便宜的那个版本已经够了**，这是 Veda2 能零成本的关键。

逐头配对看（不是中位数之比，而是每个头自己比自己）：

| ρ | 对角特征的 ε 收益中位数 | p10 | p90 | 变差的头 |
|---|---|---|---|---|
| 5% | +8.1% | −0.2% | +20.9% | 10.4% |
| 10% | +9.8% | +0.6% | +23.0% | 9.0% |
| 20% | +12.1% | +1.0% | +25.6% | 8.8% |

约 9% 的头会变差，这是因为上表用的是**写死的精确系数**。换成可学习的低秩头之后，每个头
可以把系数学到 0，这个下行基本应该消失——这也是选「可学习低秩头」而不是「硬编码公式」
的理由。

### 2.1 训练循环自己的指标：和发布的训练过的打分器三方对比

上面的 ε 是本文档自己的度量。再用 stage1 训练循环**已经在看**的指标验一遍
（`heatmap.mask_diagnostics` 的 `recall` / `heat_kept`），把**发布的 8NFE step600
打分器**也拉进来做第三方：16:9@37、ρ=0.1（与 bundle 自己的 keep_ratio 一致）、
**用 bundle 自带的方案表**（4 种 tile 形状，不是均匀的 4x4x8）、一条 clip ×
步 {0,2,5,7} × 50 层 = 2400 行。

`veda1` 是今天的打分器初始化（`second_order_rank=0`），`veda2` 是全秩低秩头加
`init_exact_second_order_()`，两者**共享同一套基础投影**（单测用 `torch.equal` 钉死），
唯一区别就是二阶头。`veda1_trained` 是发布的权重。

**目标 = `max`（Veda 现在真正蒸馏的东西）**：

| 打分器 | recall | heat_kept | kept/天花板 |
|---|---|---|---|
| veda1（未训练） | 0.5308 | 0.4929 | 0.7679 |
| **veda1_trained（600 步）** | **0.5620** | **0.5212** | **0.8119** |
| veda2（未训练） | 0.5465 | 0.5040 | 0.7852 |

**目标 = `sum`（块质量，也就是真正决定 ε 的量）**：

| 打分器 | recall | heat_kept | kept/天花板 |
|---|---|---|---|
| veda1（未训练） | 0.6935 | 0.6378 | 0.9023 |
| veda1_trained（600 步） | 0.6756 | 0.6425 | 0.9091 |
| **veda2（未训练）** | **0.7189** | **0.6468** | **0.9151** |

三件事，按重要性排：

1. **在决定 ε 的那个度量下，未训练的 veda2 已经追平甚至超过训练过的 veda1。**
   recall 0.7189 vs 0.6756（+4.3 个点），`kept/天花板` 0.9151 vs 0.9091。
   `heat_kept` 只多 0.0043（+0.7% 相对），这是加权后的量、也是更该信的那个，所以
   **别把它读成"白送 600 步训练"**；诚实的说法是：**不训练就已经不落后。**
2. **用 max 做目标把打分器往离质量更远的地方推了。** 训练过的打分器对**质量** oracle 的
   recall 比未训练的**更低**（0.6756 vs 0.6935）。`heat_kept` 还是略涨（0.6378 →
   0.6425），所以不是纯倒退，但按质量这个标准排序确实变差了。这正好印证 §1 的结构论证：
   打分器的初始化本来就在估计质量，拿块内最大值去蒸馏是在和它的自然位置对抗。
3. **在 max 目标下，二阶头白送的量约等于 600 步训练的一半。** 训练把 recall 从 0.5308
   抬到 0.5620（+3.12 点），二阶头的初始化抬到 0.5465（+1.57 点）。

要说清楚的边界：这一轮**没有训练 veda2**。它证明的是起点更好，不是训练后更好；一个训练过
的 veda2 可能更好，也可能把二阶系数学歪，没测。而且只有一条 clip、一种几何。真正的训练
对比是 §7 的待办 1 和 2。

## 2.2 端到端：真实生成、真实测速、真实视频

`recall` / `heat_kept` 只是掩码和 oracle 的重合度，不是输出质量。所以跑了完整的
8 步去噪，三路同 seed、同 prompt、同几何，并实测每步时间。

设置：1:1@37（**768×768、124 帧、21312 video token**，最小的几何）、**ρ=0.05**、
`moviegen_holdout20` 里**全部 5 条**该长度的 clip、1×RTX PRO 6000 Blackwell、
FA4 块稀疏（sm_120，vendored 补丁）。ρ=0.05 下即使 oracle 也只保住 **50~56%** 的块
质量（实测，`runs/sol_initprobe_1x1_t37`），所以这是稀疏最吃力的区间。

### 速度（5 条 clip 的均值，排除 step 0 的 kernel 编译）

| 路线 | 每步 | 注意力 | 每步加速 | 注意力加速 |
|---|---|---|---|---|
| Dense | 5.450 s | 1.920 s | 1.00× | 1.00× |
| Veda1（发布的 step600） | 3.944 s | 0.468 s | 1.38× | 4.10× |
| Veda2 rank 128，池化未融合 | 4.209 s | 0.746 s | 1.29× | 2.58× |
| **Veda2 rank 16，池化已融合** | **3.938 s** | **0.475 s** | **1.38×** | **4.04×** |

**最后一行和 Veda1 在噪声以内**（每步 3.938 对 3.944 s，注意力 0.475 对 0.468 s）。

拿到这一行需要两步，而且**顺序和直觉相反**：

1. **只降 rank 完全没有用。** rank 16 在池化还没融合时实测仍然是 4.2 s/step、注意力
   0.7 s，和 rank 128 一模一样。也就是说 +0.278 s 的开销**根本不在 n² 项上**，
   §3.1 那套「二阶项是又一个 rank-D 双线性所以要给它低秩」的成本分析，方向对但量级错了。
2. **开销全在池化。** `_gather_and_pool` 用的融合 gather kernel 只写
   `[mean|max|min]`，所以两个二阶矩原来是事后再调两次 `pool_tiles`，把 tile 序的 q/k
   又读了几遍（中心化方差还要读两遍）。把它们塞进那个 kernel 之后开销就没了：
   **tile 本来就已经在寄存器里**，连中心化方差都不要额外的内存流量，因为均值在同一个
   kernel 里刚算完。

低秩头仍然要留着，但理由变了：它省的是**参数和显存**（bundle 从 734 MB 降到 547 MB），
不是时间。

子空间里,这也说明 §3.1 的数据加权拟合是对的:它找的就是那个子空间。

### 闪烁：为什么这条观察比 ε 更重要

人工确认给出的不是「稍好」而是一个**定性的失效消失了**，而 ε 看不到它。ε 是逐层标量，
对时间维取了平均；闪烁是**时间一致性**的失效，平均之后正好被抹掉。

机制上这和「块内最大值 vs 块质量」直接对应：

- 块内最大值是**极值统计量**，由单个 token 对决定，方差大。相邻帧的同一个 query tile
  很容易因为一个 token 的抖动就换掉所选的 key 块。
- 块质量是 128×128 项的**和**，是平均统计量，方差小得多。

tile 形状是三维的（如 4x4x8 跨 4 帧），所以**选块的不稳定直接表现为跨帧上下文不一致，
也就是闪烁**。Veda1 对着极值统计量蒸馏，Veda2 对着和统计量，这是闪烁差异最自然的解释。

这给出一个可量化的代理指标：**掩码抖动**（同一 query tile 在相邻去噪步之间、以及时间上
相邻的 query tile 之间，所选块集合的重合度）。见 §7 待办。

Sol 没有进这一轮对比（用户标为可选）：它的两个机制都已被实测否掉（§5 与
[sol_ablation](sol_ablation.md) §3），而把它的 `μ+βσ` 阈值接进推理路径要改
`miowtion/veda/mask.py`，那个文件被别的 agent 占用。

复现：

```bash
python scripts/bolt_veda2.py --in <released bundle> --base reset \
    --out weights/veda/veda2_untrained.safetensors
python scripts/generate.py --config configs/infer_veda2_1x1_t37_sparse05.yaml
python scripts/generate.py \
    --config configs/infer_veda2_1x1_t37_sparse05_veda2.yaml
# then one scripts/visual_check.py per clip, three --video panes
```


## 2.3 训练：五次失败，一个共同的原因

§2.1 和 §2.2 的所有 Veda2 数字都是**完全 training-free** 的：投影是全新的 N(0,1e-4)，
二阶头和 count gain 在闭式系数上。那自然引出一个问题——训练能不能在这之上再加分。
目前的答案是「还不知道」，但五次尝试把**不是**原因的东西排除掉了，这些排除本身就是结果，
而且第五次之后它们有了**一个共同的解释**（§2.4）：损失必须对 top-k 读出看不见的那两个
规范方向（逐行偏移、逐行尺度）不变，否则梯度会去调规范而不去调排序。

接线在 `TrainConfig` 上：`second_order_rank` / `count_term` 直通打分器，
`heat_reduce` 选蒸馏目标，`kl_direction` 选 KL 方向，`kl_weight` / `topk_weight` 配比，
`freeze_second_order` 冻住二阶头。默认全是 Veda1。

### ① forward KL 和它要优化的东西反向

`seer_kl` 原本算的是 KL(teacher ‖ student)，即 **forward** 方向。Forward KL 是
**覆盖型**的：教师哪里有质量、学生在那里概率低就被重罚，所以**摊平是最便宜的降损方式**。

实测，25 步：**KL 从 134 降到 48（−65%），同期 recall 从 0.714 掉到 0.654。**
损失被最小化了，而要的东西变差了。这不是权衡，是目标选错。

它也解释了那个荒谬的量级。logit spread 为 $\sigma$ 时 $\log p_j\approx-(S_{\max}-S_j)=O(\sigma)$，
所以 forward KL $\approx\sigma(1-t_{\max})$——**最小化它等于压缩 logit 幅度**，不是学排序。

`seer_kl` 现在有 `direction`。**reverse** 是 KL(student ‖ teacher)，**寻峰型**：学生只因为
在教师没质量的地方放质量而被罚。教师的零 floor 在 1e-6，所以损失有界（约 14）而不是跑到 300。
单测钉的是两者的定义性差别：尖锐的学生在 reverse 下赢、在 forward 下输。

### ② 从 Veda1 warm start 更差，而且是 init 时就更差

直觉上该复用那 600 步学到的特征提取。实测相反，同 keep_ratio、同几何轮转、step 1：

| 初始化 | recall | logit_std | grad_norm |
|---|---|---|---|
| warm start（Veda1 训练过的基础） | 0.6310 | 192~275 | 7522 |
| from scratch（重置的基础） | **0.7557** | 192~277 | 2037 |

**重置的基础领先 12.5 个点。** 闭式项和**未训练**的基础组合得上，和**对着块内最大值训过**的
基础组合不上——和 §7 里 bolt 失败是同一个失配。600 步特征学习不值得落后 12 点开场。

### ③ reverse KL 把 logits 跑飞了

换成 reverse 之后损失量级正常了（0.275 对 209），但 48 步之内：

| 步 | recall | kept/ceiling | reverse KL | logit_std |
|---|---|---|---|---|
| 1–12 | 0.7308 | 0.9185 | 0.2872 | 111 |
| 13–24 | 0.6905 | 0.9064 | 0.3390 | 171 |
| 25–36 | 0.6573 | 0.8895 | 0.4060 | 365 |
| 37–48 | 0.6401 | 0.8821 | 0.4430 | 664 |

**损失自己在上升**，所以这不是权衡而是发散。机制是二阶头的**二次耦合**：
项是 $AB^\top$ 的双线性，$\partial S/\partial A\propto A$，而 Adam 步长与梯度大小无关，
所以 $A$（初值 0.0625）每步漂 1.6%、48 步漂 77%，乘积动 3 倍。
`freeze_second_order` 就是为这个加的；冻住之后发散消失。

### ④ 我用 12~59 步评判了一件需要几百步的事

这一条不是运行失败，是**我的判断错**，记下来因为它比前三条更容易再犯。

Adam 的步长 ≈ lr，**与参数自身尺度无关**。`proj` 初值 **1e-4**，而发布版训练之后是
**1.15e-2**。所以 lr 1e-3 是**每步 10 倍相对变化**，12 步就走完了到有用尺度的全程，
把那个物理上正确的零阶估计量覆盖成了 12 步噪声。而 Veda1 是 **600 步 + step 170 的
warm start** 才收敛的。早期回落是旅程的一部分。

于是试了 lr 1e-4（慢 10 倍），50 步**什么都没动**：逐几何都在起点 0.01 以内。
所以问题不是「精炼还是覆盖」，而是「**学一个投影**」对「**保留闭式**」，只有跑完全程能答。

### 两个 guard，各管一件事

一次下降跑了 59 步才被看到，等于一小时 GPU 花在 20 步就能看出的结论上。所以：

| | 判据 | 适用 |
|---|---|---|
| `train.monitor.EarlyAbort`（**默认开**） | `max_drop`：跌破起点超阈值 | **长跑**。两次真失败都是这个形状，且不在乎跑了多久 |
| 同上 | `patience`：trailing mean 不创新高 | 只适合短诊断跑。它曾把一次「只是平的」运行砍在第 50 步 |
| `scripts/watch_training.py` | 以上两条 + `stall` | 外部，额外抓**停止写日志**：挂在 kernel、卡在 NFS、被杀没 traceback，三种今天都发生过 |

两个判据都不给会直接报错，而不是悄悄永不开火。比较一律用 **trailing mean**，因为四个几何
轮转造成的波动比进展本身大——单步根本不可比。


### 更正：`log B` 的收益取决于块行数的**离散程度**，不是补齐比例

我原先写的是「`log B` 的收益直接取决于补齐块的比例」。**那是错的**，另一个 agent 在双采
几何上的复测（中位比 ≈1.00，平均误差略差）把它推翻了，而两边的测量都是对的。

机制：`log B_j` 是**每列一个常数**，所以给第 $j$ 列加常数只在这些常数**彼此有差别**的
程度上改变 top-k。预测量是 $\mathrm{std}_j(\log B_j)$ 相对于基础分数的 spread，
而补齐**比例**根本不是预测量——这个例子里它甚至指向相反方向：

| 几何（4x4x8） | tile 数 | 补齐比例 | **std(log B)** | 行数范围 | 相对 base spread 3.9 |
|---|---|---|---|---|---|
| 16:9@37 | 360 | **19.1%** | **0.664** | 8 ~ 128 | 17% |
| 双采第一段 8x14x72 | 72 | 12.5% | 0.302 | 64 ~ 128 | 8% |
| 双采第二段 15x27x72 | 252 | **9.6%** | **0.160** | 72 ~ 128 | **4%** |

原因是**补齐在各轴上是乘性的**。16:9@37 在 t（37/40）和 w（42/48）两个轴上同时短，
所以角落的 tile 只有 **8** 行真实 key，`log B` 跨列差到 $\log(128/8)=2.77$。双采那两个
几何只有一个轴短，没有任何 tile 低于半满，于是同样的 base spread 下杠杆小 4 倍——
**那是 null 而不是矛盾**。

`solattn.count_term_leverage(grid, shape)` 把这件事做成了**纯静态**的计算：只看
layout，不需要 GPU，所以上任何几何之前都能先查一眼这一项值不值得开。

实践上的结论：`count_gain` 本来就是**每头一个可学习标量、初值 1**，所以在没有杠杆的几何上
训练可以把它压到 0。但我不能再声称那 22~36% 是普适的——**它是 16:9@37 这个 layout 的
性质**。

### ⑤ 居中的 BCE：loss 在 3 个几何上**涨**

把 oracle top-k BCE 逐行居中（减掉该行均值）解决了「loss = 偏置」那个病：二阶项是
非负乘积之和，也就是一个很大的正偏移，居中之前那个偏移**就是** loss 本身（537，
grad_norm 7522 对着 clip 1.0）。居中之后 loss 回到 O(10)，梯度范数 0.5~0.79，
远在 clip 以下——优化器确实在做有效更新。然后：

| 几何 | n | BCE | | `kept/ceiling` | |
|---|---|---|---|---|---|
| 16:9@37 | 3 | 49.15 → 64.21 | **涨** | 0.9037 → 0.8831 | 跌 |
| 1:1@37 | 2 | 22.97 → 31.62 | **涨** | 0.9343 → 0.9346 | 平 |
| 4:3@37 | 4 | 8.86 → 13.73 | **涨** | 0.9239 → 0.9019 | 跌 |
| 9:16@37 | 4 | 26.72 → 24.29 | 跌 | 0.9091 → 0.8934 | 跌 |

（必须**逐几何**看：四个几何轮转，混在一起的曲线不可比。）

四个几何里有三个**损失和指标同时变坏**，这不是「优化目标和指标不一致」那种常见病，
而是更难看的一种：在做有效更新的前提下，被优化的那个量自己在涨。到这一步为止的五次
尝试各自都有解释，但没有**一个**解释。下一节是那个解释。

## 2.4 统一的诊断：目标必须对决策的规范不变

五次尝试是**同一个病**。top-k 读出对分数的**逐行正仿射变换完全不变**：给某一行所有
分数加一个常数，或者把整行乘 3，选出的块**一个都不变**。所以分数里有两个方向是
kernel 结构上看不见的——逐行偏移和逐行尺度。如果损失对这两个方向敏感，梯度就可以
在**不改变任何一个选择**的前提下把损失降下去，于是它就会去那里：那是最便宜的下降
方向。

| 目标 | 逐行偏移不变 | 逐行尺度不变 | 实测症状 |
|---|---|---|---|
| forward KL | ✓ | ✗ | 把 spread 压平：KL 134→48 而 recall 0.714→0.654 |
| reverse KL | ✓ | ✗ | 无限制锐化：48 步内 `logit_std` 涨 6 倍 |
| 原始 BCE | ✗ | ✗ | 饱和：loss = 偏移 = 537，grad_norm 7522 |
| 居中 BCE | ✓ | ✗ | 3/4 几何上 loss 涨（上一节） |
| **`transport_loss`** | **✓** | **✓** | 本节 |

forward / reverse KL 对尺度敏感的方式正好相反（一个 mass-covering 所以压平，一个
mode-seeking 所以锐化），这解释了为什么它们失败的形状互为镜像——也说明「换个方向」
这条路上没有答案，**两个方向都不满足判据**。

### 把 attention 读成一侧的熵正则最优传输

[arXiv 2508.08369](https://arxiv.org/abs/2508.08369) 指出 softmax attention 的一行
就是一个**一侧归一化的熵正则 OT** 问题的解：

$$p_u = \arg\max_{p \ge 0,\ \mathbf{1}^\top p = 1} \langle p, s_u \rangle + H(p),
\qquad p_{uv} = \frac{e^{s_{uv}}}{\sum_{v'} e^{s_{uv'}}}$$

块稀疏在这个框架里**不是近似，是支撑集约束**：只允许往块集合 $S$ 里的列运输。把
约束代进去，可达的最优值有闭式

$$F(S) \;=\; \max_{\substack{p \ge 0,\ \mathbf{1}^\top p = 1 \\ \mathrm{supp}(p) \subseteq S}}
\langle p, s_u \rangle + H(p) \;=\; \log \sum_{v \in S} e^{s_{uv}} \;=\; \log E_u(S)$$

于是**三件事同时掉出来**，都不需要任何近似：

1. **目标是质量，不是峰值。** $\arg\max_{|S| = k} F(S)$ 就是**按块注意力质量取
   top-k**，逐位精确。§2 里测到「块质量 ≈ 理想重要度（差 1.6%），块最大值差 7~10%」
   是经验结果；这里它是**推出来的**：$F$ 是 $\log$-sum-exp，块最大值不是任何
   OT 问题的值。这也是 `transport_weight` 要求 `heat_reduce: sum` 的原因，配置里
   直接报错而不是悄悄用错的目标。
2. **选择丢掉的价值有闭式。** 丢掉的质量占比记为 $r_u = 1 - E_u(S)/E_u(\text{all})$，
   则 $F(\text{all}) - F(S) = -\log(1 - r_u)$。这正好是 `heat_kept / heat_ceiling`
   这个指标在量的东西，也就是说**指标本身就是 OT 的次优间隙**，不是它的代理。
3. **Veda1 的未训练打分器就是零阶项。** 对 $F$ 做累积量展开，首项是
   $\log B_j + \bar Q \cdot \bar K / \sqrt{D}$——均值池化的 QK 加上块行数。这是
   §1 那个「结构性缺口」论证的 OT 版本，而且给出了缺的是**哪一项**（二阶累积量）。

### `transport_loss`：保留质量占可达质量的比例

学生不能直接输出一个集合（不可微），所以放松的**只有选择**这一步：把 k-hot 指示
函数换成关于该行自己第 k 大分数的 sigmoid——

$$z_u = \frac{s_u - \mathrm{mean}(s_u)}{\mathrm{std}(s_u)}, \qquad
\theta_u = \frac{z_{u,(k_u)} + z_{u,(k_u+1)}}{2}, \qquad
\pi_u = \sigma\!\left(\frac{z_u - \theta_u}{\tau}\right)$$

$$\mathcal{L}_u = -\frac{\langle \pi_u,\ a_u \rangle}
{\langle \mathrm{oracle}_u,\ a_u \rangle}$$

$a_u$ 是教师的块质量，$\mathrm{oracle}_u$ 是同一个预算下按 $a_u$ 取的硬 top-k，
$k_u$ 由 `select_video_blocks` 给出（**逐行**，因为 layout 规则让预算逐行不同）。
关键性质，五条都有单测：

- **$\tau \to 0$ 时它逐位等于 $-\,$`heat_kept/heat_ceiling`**，也就是判这次训练
  成败的那个指标本身。损失和指标是**同一个对象**，不可能反向移动——而 forward KL
  （KL 134→48 而 recall 0.714→0.654）和居中 BCE（3/4 几何 loss 涨）正是反向移动了。
  oracle 自己的选择给出恰好 $-1$。
- **逐行正仿射完全不变**：$z$ 把偏移和尺度都除掉，$\theta$ 又是 $z$ 的函数，所以
  $s_u + 7$、$3 s_u$、$0.01 s_u$、$5 s_u + 100$ 给出**逐位相同**的损失
  （`torch.equal` 级别，不是容差）。这是前四个目标缺的那条。
- **梯度在规范方向上恰好为零**，不是「小」：标准化的 backward 把常数方向和径向
  分量都投影掉了，所以**没有任何一次更新能花在规范上**。
- **梯度集中在 rank-k 边界**，因为 $\sigma'$ 在那里取峰值。实测 $n=360$、$k=36$、
  $\tau=0.15$：90% 的梯度权重由 **58** 个块承担，其中 76% 落在距切点 $\pm 2\tau$
  以内。
- **policy 恰好花掉预算**（$\pi$ 按 $k_u/\sum_j \pi_{uj}$ 重标定）。这条不是修饰：
  不加的话**平坦的预测器会赢**——$z \equiv 0$ 让每一列都拿 $\sigma(0)=0.5$，等于
  「每个块都留一半」，实测损失 $-1.33$，**比 oracle 还好**。那就是 forward KL 的病
  （可以靠摊平降损失）从放松里重新爬进来。$\tau \to 0$ 时 $\pi$ 已经精确是 k-hot，
  所以重标定在极限下是恒等变换，上面第一条仍然成立。

**第一版用的是整行 softmax 作为 policy，那是错的放松**，记下来因为它看起来完全合理：
在标准化分数上、$n=360$ 时，softmax 的有效支撑是 **220 个块**，只有 **39%** 的权重
落在预算之内，于是绝大部分梯度在问 kernel 永远不读的那些排名。它跑了 4 个 update
就被这个静态计算换掉了。

$\tau$ 的取法：$z$ 已标准化，所以 $\tau$ 跨头跨几何可比。标准正态在 10% 分位
（$z \approx 1.28$）的密度是 0.175，所以 $\tau = 0.15$ 的过渡带约覆盖
$0.035n$ 个块——$n=360$ 时约十来个，宽到有梯度，窄到那是**关于决策**的梯度。

实现 `veda/heatmap.py:transport_loss`，接线 `train/trainer.py:TrainConfig.transport_weight`
（与 `kl_weight` / `topk_weight` 并列，三者可加权共存；配置里
`transport_weight` 与 `heat_reduce: max` 同时出现会直接报错），配置
`configs/stage1_veda2_transport_t37.yaml`。启动一律走
`scripts/launch_training.sh <config> <tag>`，它把 trainer 和外部 watcher
作为一个整体起起来——分开起就会忘掉第二个。

## 3. 设计与不变量

### 3.1 低秩二阶头（`miowtion/veda/predictor.py`）

对角二阶项 `E[q^2] . Var(k) / (2D)` 本身就是两个 D 维向量的内积，也就是**又一个 rank-D
双线性**。所以：

- 塞进现有的 rank-D 双线性里，两项会互相挤占（`q_hat . k_hat` 只有 D 维输出，装不下
  `q̄·k̄` 和 `E[q²]·Var` 两个独立内积）；
- 给它一个独立的 rank-D 双线性，会让主导成本的 n² 项**翻倍**。

因此给它一个**低秩**的头：

```
logits = q_hat . k_hat / sqrt(D) + (sq_q @ So_q) . (var_k @ So_k)
```

`So_q`、`So_k` 是 `[num_heads, D, rank]`。n² 项的成本只增加 `rank / D`。

- `second_order_rank = 0`（默认）：**逐位等于改动前的打分器**，单测钉死。
- `second_order_rank = head_dim` 并调用 `init_exact_second_order_()`：**未训练的**打分器
  精确等于对数质量的完整对角估计，而不是零阶估计。这延续了现有设计里
  「未训练就已经是可用的块分数」那条思路。

成本账（16:9@37，366 tile，D=128，56 头，ρ=10%）。**注意：这张 FLOP 表预测错了瓶颈**，
实测开销在池化而不是 n²，见 §2.2：

| 项 | 每头 MAC | 占稀疏注意力 |
|---|---|---|
| 稀疏注意力本身 | 439 M | 100% |
| 打分器 embed（n·3D·D） | 18.0 M | 4.1% |
| 打分器双线性（n²·D） | 17.1 M | 3.9% |
| 二阶头，rank 16（n²·r） | 2.1 M | **+0.5%** |

### 3.2 池化：行数与二阶矩

`pool_tiles(x, layout, second=...)` 增加两个统计量：query 侧要原始二阶矩 `E[x²]`，
key 侧要中心化方差 `Var(x)`。`log B` 不需要新特征，它就是 `layout.valid_count`。

**方差必须两遍算**。一遍的恒等式 `E[x²] − E[x]²` 在一个块的行彼此接近时要相减两个几乎
相等的大数，而 RMSNorm 过的 key 在同一个空间块内本来就彼此接近：随机 layout 上实测相对
误差到过 **31%**，对一个要拿来排序的特征来说完全不能用。`_second_moment()` 因此先算均值
再减，按行分块以限制 fp32 临时显存，顺带把平方也放到 fp32 做。

**池化已经融合进 gather kernel**（`tile_gather_triton.gather_and_pool(..., second=True)`）。
这不是优化而是**全部开销所在**：实测只降 rank 不融合池化，每步还是 4.2 s；融合之后回到
3.94 s，和 Veda1 齐平（§2.2）。能这么干净是因为那个 kernel 本来就把整个 tile 读进了寄存器，
所以连**中心化**方差都不要额外的内存流量——均值在同一个 kernel 里刚算完，减掉它只是寄存器
上的运算。非融合路径（CPU、或 head_dim 不被 kernel 支持时）仍然走 `pool_tiles` 的两遍实现，
GPU 测试把两者对拍。

### 3.3 质量目标（`heatmap.py` / `kernels/block_heat_triton.py`）

`teacher_heat(..., reduce=)` 增加 `'sum'`：块内 `exp(s·scale − lse)` 之和，也就是块的注意力
质量，而不是块内最大值。默认仍是 `'max'`，所以现有调用点行为不变。

Triton kernel 里这是编译期分支（`SUM: tl.constexpr`），成本与 max 版本相同。
教师热力图只在**训练**期算，推理期不存在，所以这一项的推理成本严格为零。

为什么值得换：上表里 `A`（质量）补回 92~94%，`Mx`（最大）只有 64~85%，而且 `A` 与理想
重要性 `Ω` 的互 recall 是 0.941。**块质量几乎就是理想的选块目标**，而块内最大值不是。

### 3.4 静态每头预算（`solattn.py`）

H2 问过「同一个头里每行要不要各自的预算」，答案是不要（[sol_ablation](sol_ablation.md) §3）。
把同一个问题抬到**头**这一层，两条反对理由都变了：每头预算是离线校准出来的一个静态
数字，和 tile 方案表一样，所以一个头内部每行预算仍然均匀——没有负载不均衡、没有运行期
判断、没有 kernel 改动；而且分配器不是在用代理分数猜，它读的是**实测**的误差曲线。

`allocate_budget()` 在离散网格上做拉格朗日：给密度一个价格 `lam`，每个头独立选
`误差 + lam·密度` 最小的点，再对 `lam` 二分到平均密度命中目标。曲线是凸的时候这就是网格
受限问题的精确最优，并且满足通常的边际条件——**最优解处每个头的最后一个块买到的误差
下降相同**。返回的平均密度**从不超过**目标：会超的预算不叫预算。

实测（2800 个头、`proxy_topk`、同一总成本）：

| 目标 ρ | 总 ε 节省 | 每头 ρ 的 p10 / 中位数 / p90 |
|---|---|---|
| 0.071 | +3.89% | 0.050 / 0.070 / 0.091 |
| 0.102 | **+6.22%** | 0.062 / 0.100 / 0.144 |
| 0.145 | +6.12% | 0.086 / 0.148 / 0.206 |

两端是 0.00%，那是网格被钉在实测范围 [0.05, 0.206] 上的假象，不是真的没有收益：分配器
在 ρ=0.102 上已经把 p10 压到 0.062、p90 抬到 0.144，说明它还想往外推。**实测范围要放宽
才能知道真实上限**，见 §7。

## 5. 为什么零阶补偿不进 Veda2

补偿确实有效，ρ=10% 上 ε 降 10.6%，而且与选块质量互补（用 oracle 选块时收益更大）。
但等算力下它只是打平：

| ρ | 不补偿 | 补偿 | 把同样算力用来多选块 | 逐头配对：补偿更好的比例 |
|---|---|---|---|---|
| 5% | 0.34775 | 0.29657 | 0.31751（ρ'=0.0574） | 50.8% |
| 10% | 0.22109 | 0.19761 | 0.21130（ρ'=0.1070） | 58.5% |
| 20% | 0.13016 | 0.12028 | 0.12658（ρ'=0.2062） | 62.7% |

补偿一个丢弃块的成本是精确算一个块的 1/128（一次 `q·K̄` 加一次 `p̂·V̂`，对 128 个 key），
所以 ρ' 是把补偿的算力原样换成更多块之后的密度。

**中位数之比和逐头配对给出的结论不同，要用后者。** 按中位数之比，补偿（+14.7%）明显胜过
多选块（+8.7%）；但逐头配对下补偿只在 50.8~62.7% 的头上更好，ε 比值中位数 0.988~0.998，
也就是**只好 1% 左右**。两个臂的 ε 分布形状不同，中位数之比把差距放大了。配对才是同一个
头自己和自己比。

再加上 §5 的两项工程现实：块稀疏主循环遍历**被选中**的 18 个块而补偿要遍历**补集**的 348
个，需要独立 kernel 再借主 kernel 的 LSE 合并分子分母，反向也要重推；以及约 2% 的头会
**灾难性变差**（最差 −424%，集中在第 0、1 层，均场近似最差的地方）。换 1% 不值。

### 「训一个 adaptor 预测修正权重」：等成本上界已经否掉了

Sol 的补偿是「猜一个权重」乘「块内 V 均值方向」。把权重换成**真实的** `E_uj` 就是任何
权重预测器的等成本上界（每个丢弃块一个标量，和 Sol 一样），实现为 `c=2`：

| ρ | c=0 | c=1（Sol 猜的权重） | c=2（精确权重，等成本） |
|---|---|---|---|
| 5% | 0.34775 | 0.29657（+14.7%） | 0.29602（**+14.9%**） |
| 10% | 0.22109 | 0.19761（+10.6%） | 0.20445（**+7.5%**） |
| 20% | 0.13016 | 0.12028（+7.6%） | 0.12836（**+1.4%**） |

**把权重做准不但没用，密度一高还更差。** 原因在 §3 的拆解里：`c=2` 的分母是精确的 1，
它修掉了质量估计的 100% 误差，剩下的误差全部是**块内方向**——「块里到底是哪几个 key 被
attend 到」。给一个方向错误的向量配上更大更准的权重，只会把错误放得更大。单测
`test_oracle_mass_compensation_is_exact_when_v_is_block_constant` 钉死了这个分解：把每个
块的 V 设成块内常量（方向误差为零），`c=2` 的 ε 精确为 0，而 `c=1` 不是。

所以要在补偿上下功夫，该改的是**方向**而不是权重，而方向是每块一个向量，那就是 VSA 粗
粒度分支，本仓库已知它 fully train 之后无收益。

## 6. 测试

`tests/unit/test_veda_predictor_mask.py`：
- 二阶池化对拍逐 tile 的 masked 统计量（rtol 1e-5）；拒绝未知的 `second`
- **紧致 tile**（各行几乎相同）下方差仍非负且与直算一致——一遍恒等式在这里会丢掉几乎所有
  有效位，所以两遍不是锦上添花
- `second_order_rank=0` 与改动前**逐位相同**（`torch.equal`），且不产生 `so_*` 参数
- 全秩 + `init_exact_second_order_()` 精确等于闭式的 `q̄·k̄/√D + E[q²]·Var(k)/(2D)`
- 参数量恰好多 `2·L·H·D·rank`；rank 越界、全秩要求、特征与 rank 必须同时给出都报错

`tests/unit/test_veda_heatmap_attention.py`：
- `reduce='sum'` 对拍稠密教师概率的块内求和；**每行概率和为 1，所以一个 tile 的质量等于
  它的真实行数**，这条用来独立校验归一化
- mass 必然 ≥ peak 且确实不同；未知 reduce 报错
- `transport_loss` 对**逐行正仿射**（`+7`、`×3`、`×0.01`、`×5` 再加逐行 100）
  给出**逐位相同**的损失——这是 §2.4 的判据，所以它是等式测试而不是容差测试
- **$\tau \to 0$ 时逐位等于 $-$`heat_kept/heat_ceiling`**：拿同预算的硬 top-k
  独立算一遍比对；oracle 自己的选择给出恰好 $-1$
- 「对准 < 平坦 < 对错」，且 $\tau \le 0$ 报错
- 梯度逐列求和为 0、与居中分数正交（规范方向恰好为零），且远离切点的列不带梯度
- 被排除的列和全零的行不参与

`tests/unit/test_veda_solattn.py`（56 项）：
- **跨模块对拍**：`solattn` 离线量的 `proxy_diag` 与 `predictor` 的低秩头是同一个公式，
  两份独立实现互相钉死
- `log B` 项只对每列是常数偏移，且不超过 `log 128`

- 块常量 key 下二阶项精确消失
- 预算分配器：命中平均密度且**从不超支**、与均匀分配在各头相同时一致、在实测边界上不会
  因 `exp(log(x))` 漂移而判成越界、曲线不下降时报错
- `scorer_report` 的「补回差距比例」在两端恰好 0 和 1
- 旧 run 的 json（没有 recall 字段）仍能读入

## 7. 待办（按价值排序）

1. **跑完一次完整的训练**，用 §2.4 推出来的 `transport_loss`
   （`configs/stage1_veda2_transport_t37.yaml`）。前四个目标都对决策看不见的规范方向
   敏感，这个不敏感；但「训练能不能在闭式之上加分」仍然没有答案：需要 lr 1e-3 跑满
   400 步，约 5 小时。在那之前不要对训练下任何结论。
2. **放开二阶头**（`freeze_second_order: false`）**要先换参数化**。现在它在
   `so_q`/`so_k` 上是二次的，所以会跑飞（§2.3 ③）。该改成
   `g_h · (归一化的项)`，`g_h` 是每头一个标量（线性、良条件），子空间冻结或给低一两个
   数量级的 lr。这把「这个特征值多少」和「哪个子空间」解耦。
3. **三类参数必须分 param group**：`proj` 初值 1e-4、`so_*` 0.0625、`count_gain` 1.0，
   差四个数量级，而 Adam 步长与初值无关。统一 lr 对三者分别是每步 10 倍 / 1.6% / 0.1%。
4. **放宽预算分配的实测范围**到 ρ∈[0.02, 0.4]，现在的 6.2% 是被 [0.05, 0.206] 的网格
   夹住的下界。
5. **把发布的打分器放进 ε 的度量里**。§2.1 已经在 recall / heat_kept 上量过它，但
   §2 那张「补回差距比例」的表里所有「proxy」仍然是**未训练**的池化分数。把
   `veda1_trained` 的 logits 接进 `scorer_masks` 就能补上这一格。
6. 在 `count_term_leverage` 低的几何上复跑一遍完整的 Veda2（不只是 `log B`）：
   二阶项没有这个 layout 依赖，所以它在双采 regime 上应该仍然有效，但没有实测。
7. 打分器的**去噪步条件化**：现在打分器不吃 t，而实测丢弃质量从 step 0 的 0.431 降到
   step 7 的 0.252，最优排序可能随步漂移。
